# 0010. コネクタが必要な処理の定期実行を見送り手動起動で運用する

- ステータス: 採用
- 日付: 2026-08-15

## コンテキスト

web クリップの取り込みと、今後作る朝のブリーフィングは、どちらも Google のコネクタ（ドライブ・カレンダー）を必要とする。これらを毎朝自動で走らせたい。

2026-08-14 に MCP 経由の Routine 作成を試し、`connectors` パラメータが組織で無効であること、コネクタなしの Routine からは Drive を読めないことを実測した。このとき「UI からなら作れる」と推測して 0009 に書いたが、2026-08-15 に UI で確認したところ Connectors 欄が「利用可能なコネクタがありません」だった。API と UI という独立した2経路が一致したため、このアカウントでは Routine にコネクタを載せられないと確定した。

ただし Routine のクラウド環境から `*.googleapis.com` へは到達できる（既定の許可ドメインに含まれ、実測で確認）。コネクタを介さず Google API を直接叩く道は残っている。

## 決定

**コネクタを必要とする処理は定期実行せず、依頼による手動起動で運用する。**

- web クリップの取り込みは、声をかけられたときだけ実行する
- 今後の機能も手動起動を前提に設計し、スキルは起動方法に依存しない作りを保つ
- 自動化が要るようになった時点でサービスアカウント方式を再検討する

## 結果

良い影響: 追加の認証情報を持たずに済み、実装コストもかからない。既存のスキルは起動方法から独立しているため変更不要。

悪い影響: 声をかけ忘れると受け皿に溜まる。「必要なタイミングで自動的に情報が出てくる」形は成立せず、こちらから尋ねる運用になる。

## 検討した代替案

- **サービスアカウント方式**: 鍵を環境変数に置き Google API を直接叩く。権限は共有したフォルダ・カレンダーだけに絞れ、`add-clip.sh` も変更不要。ただし初期設定と読み取り部分の書き換えで半日かかり、鍵を環境に置く必要がある。現時点の自動化の価値に見合わないため見送り、ブリーフィング作成時に再検討する
- **OAuth リフレッシュトークン方式**: フォルダ単位に権限を絞れず Drive 全体の読み取り権限になるため却下
- **Apps Script から GitHub へ push**: Claude 側に鍵は不要だが、`add-clip.sh` が持つ slug 生成・重複判定を作り直すことになり、仕組みが2か所に分かれるため却下
