# 0005. タスクのステータス todo を draft と ready に分割する

- ステータス: 採用
- 日付: 2026-08-09

## コンテキスト

Obsidian vault のタスクは frontmatter の `status`（`todo` / `doing` / `done`）で状態を持つ（`docs/adr/0004-task-status-in-frontmatter-not-directory.md`）。この構成には3つの問題がある。

1. `todo` が「起票済み・未着手」と「着手してよい」を兼ねている。`rg -l '^status: todo' tasks/` で拾えるのは未着手であって着手可否ではない
2. `claude/rules/obsidian-task.md` は「判断点 A が1つでも残っているタスクは作成しない」と定めており、検討が残る案件は起票すらできない。会話が終わると検討結果が失われる
3. `claude/rules/todoist.md` は同じ「着手してよい状態」を `ready` ラベルで表現しており、同一概念に2つの語彙がある

## 決定

**`status` を `draft` / `ready` / `doing` / `done` の4値にし、`todo` を廃止する。**

- `draft`: 実施可否や不明点の検討が残っている。着手してはならない
- `ready`: 担当者が判断なしで作業を開始できる

**起票は常に `draft` で行い、`ready` への昇格は人手判断のみとする。** Claude は自身の判断で `ready` を付けない。`claude/rules/todoist.md` の `ready` ラベル運用と揃える。

これに伴い `claude/rules/obsidian-task.md` の「タスクを作成してよい条件」は「`ready` にしてよい条件」へ位置づけを移す。判断点 A が残る案件は起票を諦めるのではなく `draft` で残す。

## 結果

良い影響: 検討途中の案件に置き場ができ、相談の結果が失われない。`rg -l '^status: ready' tasks/` が着手対象そのものを意味する。Todoist ルールと語彙が一致する。人手の昇格が着手可否のレビュー機会になる。

悪い影響: 起票から着手までに必ず人手の操作が挟まる。昇格を忘れると `draft` に滞留し、Claude 側からは作業対象が無いように見える。既存タスクとルール文の書き換えが必要になる。

## 検討した代替案

- **`draft` を足し `todo` を残す**: 移行が不要だが、`todo` が「着手可能」を意味することが伝わらず、語彙の重複も解消しないため却下
- **`status` は `todo` のまま別キー（`ready: true`）で持つ**: 状態が2軸になり Bases のグループ化と `rg` 抽出が複雑になるため却下
- **Claude も条件を満たせば `ready` を付けてよい**: 手間は最小だが、`status` は複数環境からの二重着手を防ぐ札でもあり、着手可否を自動化すると札としての信頼性が下がるため却下
- **現状維持**: 上記1〜3の問題がそのまま残るため却下
