# 開発ルール

コードを変更する作業に適用する。

## 実装後の品質確認

実装したら、次の2点を行うこと。該当する目的のスキル／コマンドが利用可能であれば積極的に活用する。

- コードの品質を確認・改善する。
- 自分が書いたコードをレビューし、指摘があれば修正する。

## コメント

コードから読み取れることは書かず、コードから読み取れないことを書く。

- 処理内容の言い換えは書かない。コードを読めば分かる。
- 書く価値があるのは「なぜそうしたか」。特に、他の選択肢がありえた場面での判断理由。
- 対象のコードとは別の場所にある情報（別ファイルの内容・設定値の意味など）を説明しない。その情報が変わったときに追従できず陳腐化する。
- 調査や議論の経緯をそのまま残さない。作業中に判明した事実であっても、読み手が必要としないなら書かない。記録として残す価値があるなら ADR 等の適切な置き場を検討する。
- 書くと決めた内容も、できるだけ簡潔にする。同じことを伝えられるなら短い方を選ぶ。

## コミット

- コミットする際は、論理的な変更ごとに分けること。
