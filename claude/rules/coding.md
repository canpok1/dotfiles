# 開発ルール

コードを変更する作業に適用する。

## 作業の進め方

1. 着手前に `TaskCreate` でチェックリストを作る。下のテンプレートをコピーし、作業に合わせて増減させる。
2. 工程に入るとき `TaskUpdate` で `in_progress` にする。
3. 工程を終えるごとに `TaskUpdate` で `completed` にする。まとめてチェックしない。
4. 想定外の工程が出たら `TaskCreate` で足す。省くときは理由をユーザーに伝える。
5. プルリクエストを作らないリポジトリでは、「プルリクエストを作成する」を「main へマージする」と読み替える。

### チェックリストのテンプレート

- [ ] 変更方針を決める
- [ ] 実装する
- [ ] テスト・lint・ビルドを通す
- [ ] コミットする
- [ ] ドキュメント・ADR への反映を確認する
- [ ] ブランチの差分を自分でレビューする（`/code-review` が使えれば使う）
- [ ] レビューの指摘を修正する
- [ ] プルリクエストを作成する

## コメント

コードから読み取れることは書かず、コードから読み取れないことを書く。

- 処理内容の言い換えは書かない。コードを読めば分かる。
- 書く価値があるのは「なぜそうしたか」。特に、他の選択肢がありえた場面での判断理由。
- 対象のコードとは別の場所にある情報（別ファイルの内容・設定値の意味など）を説明しない。その情報が変わったときに追従できず陳腐化する。
- 調査や議論の経緯をそのまま残さない。作業中に判明した事実であっても、読み手が必要としないなら書かない。記録として残す価値があるなら ADR 等の適切な置き場を検討する。
- 書くと決めた内容も、できるだけ簡潔にする。同じことを伝えられるなら短い方を選ぶ。

## コミット

- コミットする際は、論理的な変更ごとに分けること。
