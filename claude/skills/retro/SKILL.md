## このスキルの担当範囲

**示唆を出すところまで。反映も、反映先の決定もしない。** 出した示唆を採用するか、どこへ書くかはユーザーが決める。

反映まで担当すると、振り返るたびにルールやドキュメントが書き換わり、採否の判断が入らないまま増えていくため。反映先の**候補**を挙げるのは示唆の一部として行ってよい（決定と実行はしない）。

## 起動タイミング

| | 条件 |
|---|---|
| 起動する | ・自分の出力・判断の誤りが判明して修正した後で、原因が**解釈・前提・手順**のいずれかにあるとき<br>・説明や提案がユーザーに通じず、やり直しになったとき<br>・同じ種類の誤りが2度目だと気づいたとき（記録が無くても、その会話の中で2度目なら該当）<br>・ユーザーが「振り返って」と言ったとき（手動起動） |
| 起動しない | ・タイポ・パス誤り・ツールの一時的失敗など、原因が一目で分かり「直す」で終わるもの<br>・ユーザーの要望変更・追加による手戻り（こちらの誤りではない）<br>・原因がまだ特定できていない段階（掘っても空回りする）<br>・同じ会話で既に retro を回した同種の事象 |

**起動条件の軸は誤りの大きさではなく、原因が構造にあるかどうか。** 打ち間違いを掘っても「気をつける」しか出ない。解釈・前提・手順に原因があるものは、書き方や手順を変えれば次から防げる。

うまくいったことの振り返りは**自動起動しない**（「うまくいった」のシグナルが弱く、自動で拾うと自画自賛が増える）。手動起動のときだけ扱う。

## 手順

### ステップ1: 事実を確定する

- 何が起きたか、どの時点で分かれたかを、**推測と分けて**並べる
- 原因がまだ特定できていないなら、先にそこを詰める。不明なまま次へ進まない

### ステップ2: 突っ込み役のサブエージェントへ説明する

Agent ツールでサブエージェントを起動し、確定した事実と、自分が見立てた原因を説明する。

- **サブエージェントが会話の文脈を持たないことは、欠点ではなく検証装置。** 文脈を持たない相手に通じる説明になって初めて、原因を掴めたと言える。通じなければ言い換える
- 専門用語・内部の言い回しに逃げない。「〜を遡って修正した」のような自分にだけ自明な説明は通じない
- 往復は2〜3回まで。それ以上続くなら、原因の特定自体ができていない（ステップ1へ戻る）

### ステップ3: 観点を渡して掘らせる

サブエージェントへ次の観点を渡し、示唆の候補を潰させる。

| 観点 | 問い |
|---|---|
| 既存対策 | すでにルール・手順はあるか。**あるならなぜ効かなかったか** |
| 前提の要否 | そもそもその構造・手順は必要か。無くせば問題ごと消えないか |
| 対策の種類 | その対策は**前提知識を覚えていること**に依存していないか。知らなくても防げる形にできないか |
| 抽象度 | 広すぎて使えないか。狭すぎて別のケースで破れないか |
| 効く範囲 | この場限りか。他のどこに当てはまるか |
| 行動可能性 | それを読んだ人（Claude を含む）は、何をすればよいか分かるか |

**「対策の種類」が一番効く。** ルールを増やす対策は、読み手がそれを思い出さない限り破れる。書き方・構造の側を変えれば、ルールを知らなくても防げる。

### ステップ4: 示唆をまとめて提示する

次の形で出す。1件ずつ書き、無理に数を揃えない。

```
- 何が起きたか: <1文>
- なぜ起きたか: <1文。表面の事象ではなく、何がどうなると壊れるか>
- 次にどうするか: <「〜のとき〜する」の行動の形>
- 効く範囲: <この場限り / 他にも当てはまる（どこか）>
- 反映先の候補: <ルール・スキル・記録・タスク・不要。決定はしない>
```

## 示唆の書き方

- **行動の形で書く。** 「〜に気をつける」「〜を意識する」は行動ではない。読んだ人が何をすればよいか分かる形にする
- **「示唆なし」で終えてよい。** 一度きりの事象まで示唆を出すと、採用側で捨てる手間だけが増える
- 対策の抽象度・置き場所・汎用化の考え方は `CLAUDE.md` の「再発防止策は汎用化してから入れる」に従う。ここでは重複させない

## うまくいったことを振り返るとき

掘る観点が違う。ステップ2〜3を次に置き換える。

- **偶然か、構造によるものか。** 条件が揃っただけなら次は再現しない
- 再現するには何が要るか（前提・順序・道具）
- 他の場面へ移せるか。移せないなら何が障害か
