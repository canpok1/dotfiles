タスクの登録先・ラベル運用はタスク管理ルールに従う。

## 手順

- [ ] ステップ1: タスクの内容を確認する
- [ ] ステップ2: タスクの要件に沿って対応を行う
- [ ] ステップ3: （実装した場合）開発ルールに従い、コード品質の確認・改善と自己レビューを行う
- [ ] ステップ4: （実装した場合）プルリクエストを作成する
- [ ] ステップ5: （実装した場合）作成したプルリクエストのCI確認・レビュー対応・マージを行う
- [ ] ステップ6: 作業メモとこれまでの文脈をもとに振り返りを行う

## 注意点

- 共通
    - 各ステップで該当する目的のスキルが利用可能であれば積極的に活用すること（例: コード品質の改善、コードレビューなど）。
    - 節目ごとに作業メモを残し、後続の作業で参照できるようにすること。
    - コマンドやツールの実行結果が空・想定外だった場合は、次のアクションへ進む前に状態確認を挟むこと。例: タスク取得が空なら検索条件を見直して再取得、空出力・無出力のコマンド直後はその結果を別途確認、リソースの削除・移動の前後では存在や状態を確認する。
    - **作業を進められない状況になったら、理由をコメントしてから `ready` ラベルを外す** — 要件が不明確で確認待ち・依存タスクが未完了・前提が崩れている等で作業を継続できないと判断した場合は、次の順で対応すること。
        1. 進められない理由（何が・なぜ進められないか、再開に必要な条件）をタスクにコメントする。
        2. その後にタスクから `ready` ラベルを外す（ラベル更新は全置換になり得るため、現ラベルから `ready` のみ除いて指定する）。ラベル運用はタスク管理ルールに従う。
        - コメントを残す前に `ready` を外さないこと（再開時に理由が追えなくなるのを防ぐ）。
- ステップ1
    - 引数 `$ARGUMENTS` が指定されている場合はそのタスクIDのタスクを対象にすること。
    - タスクを特定できない場合や完了済みの場合はユーザーに報告し、続行するか判断を仰ぐこと。
    - タスクの内容（タイトル、本文、ラベル、コメント等）から実装要件を整理すること。
    - 要件が不明確な場合はユーザーに確認すること。
    - 着手したら `in-progress` ラベルを付与する（ラベル運用はタスク管理ルールに従う）。
- ステップ2
    - コードやファイルの変更については開発ルールに従うこと（コミット粒度、ドキュメントへの反映など）。
- ステップ6
    - 対応が完了したらタスクを完了にするか、ユーザーの運用に従って状態ラベルを更新すること。
