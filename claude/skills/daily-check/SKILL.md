# 毎日の定期作業

**会話イベントに依存しない起点として動く。** 「食事の報告を受けたら確認する」のような会話内のきっかけは、セッションが切り替わると消える。このスキルは定期起動から呼ばれ、会話が無い日でも確認を回す。

**起動方法には依存しない。** 手動で呼んでも定期起動から呼ばれても同じ動作をする。

## 前提

**[[obsidian-vault]] の clone が無ければ何もせず終了する**（エラーにはしない）。確認項目が vault の記録に依存するため。**記録するかどうかは clone を用意しているかでユーザーが制御する**（`work-log` と同じ）。

clone の探索順も `work-log` に合わせる。`$OBSIDIAN_VAULT_DIR` → 作業中のリポジトリの兄弟ディレクトリ → `$HOME/obsidian-vault` → `$HOME/src/obsidian-vault`。

**確認を始める前に、vault と dotfiles の clone を最新化する**（`git pull --rebase origin main`）。定期起動のセッションは**コンテナ作成時の clone を使い続ける**ため、放置すると古いノートを読み、古い手順のまま動く。

## 手順

### 1. 確認項目を順に実行する

| 項目 | 委譲先 |
|---|---|
| 食事管理のサイクル | `meal-management` スキルの「サイクルの起点に自分で気づく」 |

**この表に書くのは「どのドメインの何を確認するか」だけにする。** 何を見てどう判断するかは委譲先のスキルが持つ。ここに具体的な手順を書くと同じ内容が2か所に分かれ、片方が古くなる。

**確認する範囲は当日と翌日。** 当日分だけ見ると、深夜に実行されたときに対応できる時間が数時間しか残らない。

### 2. 見つかったことに対応する

| 種類 | 対応 |
|---|---|
| 確認が要らず、その場で直せる | 直す |
| 現物の確認が要る（在庫の実物など） | 直さずに通知する |
| ユーザーの判断が要る（日程・方針など） | 決めずに通知する |

**無人で動く前提なので、判断が要るものを勝手に確定させない。** 下書きを作って残すのはよいが、確定させて後続の作業まで進めない。**確認できない前提を「たぶんこうだろう」で埋めない。**

### 3. 通知する

**対応が必要なことがあったときだけ** `PushNotification` を送る。

- 問題が無かった日、自動で直して完結した日は通知しない
- **深夜に実行されることがある。** 通知の到達時刻は選べないため、急ぎでない用件も同じ経路で届く

### 4. 記録する

**毎回** `work-log` スキルでデイリーノートへ追記する。

- 対応することがあった日は、何を直し何を通知したかを書く
- **対応が不要だった日も1行だけ残す**（例: 「daily-check 実行、対応なし」）。**痕跡が無いと「動いて何も無かった」と「動かなかった」を区別できない**（2026-09-02 の初回実行でこの区別に困り、`list_triggers` の `last_fired_at` を見に行くことになった）
- **対応が無い日を長く書かない。** 1行に収める。毎日の記録が本文で埋まると、実際の変化を探しにくくなる

## 項目を増やすとき

- 手順1の表に1行足す。**委譲先のスキル名と、確認するものの名前だけを書く**
- 確認の手順は委譲先のスキル側に書く。このスキルには書かない
- **ユーザー確認なしでは完結しない項目も足してよい。** 手順2の分類に従って通知へ回るため、確認が要ること自体は問題にならない

## 防げないこと

- **定期起動が止まったこと自体は検知できない。** 起動されなければこのスキルは動かない。停止の検知は持たない（`obsidian-vault` の `projects/obsidian-vault/adr/0005-periodic-execution-via-session-bound-routine.md`）
- **通知に気づかなかった場合。** 送るところまでが担当で、既読は追わない
