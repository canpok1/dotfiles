# 毎日の定期作業

**会話イベントに依存しない起点として動く。** 「食事の報告を受けたら確認する」のような会話内のきっかけは、セッションが切り替わると消える。このスキルは定期起動から呼ばれ、会話が無い日でも確認を回す。

**起動方法には依存しない。** 手動で呼んでも定期起動から呼ばれても同じ動作をする。

## 前提

**[[brain]] の clone が無ければ何もせず終了する**（エラーにはしない）。確認項目が brain の記録に依存するため。

clone はセッションのワークスペースから探す。**このスキルは記録に `work-log` スキルを使うが、`work-log` は brain の中にあるため、`--add-dir` で brain を参照させていないセッションでは使えない。** 定期起動の Routine では brain を参照させておく。

**確認を始める前に、brain と dotfiles の clone を最新化する**（`git pull --rebase origin main`）。定期起動のセッションは**コンテナ作成時の clone を使い続ける**ため、放置すると古いノートを読み、古い手順のまま動く。

確認の依頼に使う `google-tasks` は `canpok1/google-tasks-bridge` にあるため、Routine ではこのリポジトリも参照させておく（無いときの扱いは手順3）。

委譲先のスキルが別のリポジトリにある場合は、そのリポジトリも同じように最新化する（`life-log-import` は `canpok1/life-log` にある）。**ただしスキル本体はセッション開始時に読み込まれるため、最新化しても手順が新しくなるのは次回の起動から**。

## 手順

### 1. 確認項目を順に実行する

| 項目 | 委譲先 |
|---|---|
| 食事管理のサイクル | `meal-management` スキルの「サイクルの起点に自分で気づく」 |
| 食事管理のルール化候補 | `meal-management` スキルの「ルール化候補の棚卸し」 |
| 生活費の取り込み | `life-log-import` スキル（`life-log` リポジトリ内）の「定期実行から呼ばれるとき」 |
| 作業ログの集約 | `archive` スキル（brain リポジトリ内） |
| リマインドの反映 | `reminder` スキル（brain リポジトリ内） |
| 未判断タスクの滞留 | `task-refine` スキルの「定期実行から呼ばれるとき」 |

**この表に書くのは「どのドメインの何を確認するか」だけにする。** 何を見てどう判断するかは委譲先のスキルが持つ。ここに具体的な手順を書くと同じ内容が2か所に分かれ、片方が古くなる。

**確認する範囲は当日と翌日。** 当日分だけ見ると、深夜に実行されたときに対応できる時間が数時間しか残らない（日付で範囲が決まる項目に限る）。

**項目ごとに前提が揃わないことがある。** 委譲先が「前提が無いので何もしない」と返したら、それは正常系として扱い、次の項目へ進む。1項目の不成立で全体を止めない。

### 2. 見つかったことに対応する

| 種類 | 対応 |
|---|---|
| 確認が要らず、その場で直せる | 直す |
| 現物の確認が要る（在庫の実物など） | 直さずに確認を依頼する |
| ユーザーの判断が要る（日程・方針など） | 決めずに確認を依頼する |

**無人で動く前提なので、判断が要るものを勝手に確定させない。** 下書きを作って残すのはよいが、確定させて後続の作業まで進めない。**確認できない前提を「たぶんこうだろう」で埋めない。**

### 3. 報告と確認の依頼を分けて出す

**報告は Slack、ユーザーへの確認の依頼は Google ToDo に出す**（`docs/adr/0013-user-confirmation-as-google-tasks.md`）。報告と同じ1通に確認を混ぜると埋もれ、回答されないまま毎日通知だけが積み上がる（2026-10-18〜10-22、間食の日曜の確認）。

| 出すもの | 経路 |
|---|---|
| 報告（直したこと・状況） | Slack の #notification |
| 確認の依頼（手順2で「確認を依頼する」としたもの） | Google ToDo に1件1タスク。`google-tasks` スキル（`canpok1/google-tasks-bridge` 内）で登録する |

- **ToDo は、何を答えればよいかがタイトルだけで分かるように書く**（例: 「お菓子の箱の残りを報告」）。期限は回答が要る日、補足はメモ欄
- **登録の前に未完了の ToDo を引き、同じ確認があれば作らない。** 未回答のまま毎日作り直すと重複する。未回答が続いていることは Slack の報告に書く
- **回答を受けたセッションが、その ToDo を完了にする**
- ToDo に登録できないとき（`google-tasks` が読み込まれていない、接続情報が無いなど）は、確認の依頼も Slack に出し、登録できなかったことを書く
- 問題が無かった日、自動で直して完結した日は Slack に送らない
- **深夜に実行されることがある。** 送る時刻は選べないため、急ぎでない用件も同じ経路で届く

### 4. 記録する

**毎回** `work-log` スキルで記録を残す。

- 対応することがあった日は、何を直し、何を報告し、何の確認を依頼したかを書く
- **対応が不要だった日も1行だけ残す**（例: 「daily-check 実行、対応なし」）。**痕跡が無いと「動いて何も無かった」と「動かなかった」を区別できない**（2026-09-02 の初回実行でこの区別に困り、`list_triggers` の `last_fired_at` を見に行くことになった）
- **対応が無い日を長く書かない。** 1行に収める。毎日の記録が本文で埋まると、実際の変化を探しにくくなる

## 項目を増やすとき

- 手順1の表に1行足す。**委譲先のスキル名と、確認するものの名前だけを書く**
- 確認の手順は委譲先のスキル側に書く。このスキルには書かない
- **ユーザー確認なしでは完結しない項目も足してよい。** 手順2の分類に従って確認の依頼へ回るため、確認が要ること自体は問題にならない

## 防げないこと

- **定期起動が止まったこと自体は検知できない。** 起動されなければこのスキルは動かない。停止の検知は持たない（`brain` の `projects/brain/adr/0005-periodic-execution-via-session-bound-routine.md`）
- **報告や ToDo に気づかなかった場合。** 出すところまでが担当で、既読は追わない
